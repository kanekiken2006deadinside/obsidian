## Кейс 1. «Стартап или нет?»

**Что это такое: проект, бизнес или стартап?**

Это стартап — и вот почему важно разграничивать эти понятия.

Проект — это ограниченная по времени деятельность с конкретным результатом (например, «сделать приложение к декабрю»). После достижения результата проект заканчивается. У студенческой команды нет признаков завершённости — они явно планируют продолжать.

Бизнес — это устойчивая модель, которая уже генерирует доход по понятной и повторяемой схеме. Есть клиенты, есть деньги, есть отлаженные процессы. У команды этого нет: один вуз, код «на коленке», денег нет.

Стартап — это временная организация, созданная для поиска масштабируемой и воспроизводимой бизнес-модели в условиях высокой неопределённости (классическое определение Стива Бланка). Именно это и происходит: команда проверяет гипотезу (расписание → реклама → деньги), пытается масштабироваться, действует в условиях полной неопределённости. Всё сходится.

**Какую методологию управления выбрать?**

Waterfall здесь не подойдёт: требования неизвестны, рынок не проверен, всё будет меняться.

Оптимальный выбор — Lean Startup + Agile-разработка. Lean Startup даёт принцип «строй — измеряй — учись»: сначала выпускаем минимально жизнеспособный продукт (MVP), проверяем, нужен ли он рынку вообще, затем итерируем. Agile (например, Scrum) позволяет разрабатывать итерациями по 1–2 недели, быстро реагировать на обратную связь пользователей и не тратить месяцы на то, что потом окажется ненужным.

Конкретная рекомендация: прежде чем писать «нормальный» код, провести 20–30 интервью с организаторами мероприятий (будущими рекламодателями) и студентами, чтобы проверить ключевые гипотезы. Только потом — полноценная разработка спринтами.

## Кейс 2. «HADI для кофейни»

HADI-цикл — это структура для быстрой проверки бизнес-гипотез: Гипотеза → Действие → Данные → Инсайт.**Г — Гипотеза:** комбо «кофе + круассан» за 250 руб. (вместо 270 руб. по отдельности) увеличит средний чек минимум на 15% за счёт того, что клиенты будут брать еду чаще.

**А — Действие:** в течение 2 недель добавить позицию в меню, поставить табличку на кассе, обучить кассира произносить фразу «Хотите круассан к кофе — вместе дешевле?».

**D — Данные:** фиксируем ежедневно: средний чек, количество проданных комбо, общую выручку. Сравниваем с аналогичными 2 неделями прошлого месяца.

**I — Инсайт (решение):** если средний чек вырос на ≥15% — масштабируем (добавляем другие комбо, делаем рекламу). Если вырос слабее — меняем гипотезу (другая цена? другой продукт?). Если не вырос вообще — изучаем почему (не предлагали? не хотели? неудобная цена?).

## Кейс 3. «Почему не летит?»

1000 лидов, 10 продаж — конверсия 1%. Средний показатель для онлайн-курсов — 2–5%. Команда ошибочно ставит диагноз «плохой маркетинг», но это симптом, а не причина.

**Инструменты для поиска корневой проблемы:**

CustDev (Customer Development) — глубинные интервью с теми, кто получил лид, но не купил. Ключевые вопросы: «Что вас остановило?», «Что должно было быть иначе, чтобы вы купили?». Это даст качественное понимание барьеров.

CJM (Customer Journey Map) — карта пути клиента от момента, когда человек увидел рекламу, до момента, когда закрыл страницу. Нужно найти, на каком шаге происходит наибольший отток: видит рекламу → кликает → попадает на лендинг → смотрит программу → видит цену → уходит. Где именно?

HADI — можно протестировать конкретные гипотезы-исправления. Например, изменить заголовок лендинга и замерить, вырастет ли конверсия с клика на «оставить заявку».

**Три возможные причины, не связанные с качеством контента:**

Первая — доверие. Аудитория не знает авторов курса, нет отзывов, нет кейсов выпускников, нет публичности. Люди платят незнакомцам неохотно, особенно за дорогой продукт.

Вторая — несоответствие оффера ожиданиям. Реклама обещала одно («научись управлять проектами за месяц»), а программа курса выглядит сложно, долго или слишком академично. Разрыв между обещанием и реальностью убивает конверсию.

Третья — проблема с ценообразованием и структурой оплаты. Возможно, цена кажется высокой без объяснения ценности, нет рассрочки, нет бесплатного пробного урока. Люди хотят «попробовать перед покупкой», особенно в образовании.

## Кейс 4. «Роли в проекте» — RACI-матрица**Как внедрить RACI-матрицу — пошаговый план:**

Шаг 1: Собрать всю команду и составить список всех регулярных задач проекта (не разовых, а тех, что возникают постоянно).

Шаг 2: Для каждой задачи договориться: кто делает (R), кто несёт итоговую ответственность перед заказчиком (A), кого спрашивают при решении (C), кому просто сообщают результат (I).

Шаг 3: Проверить два правила: в каждой строке должна быть ровно одна буква A (иначе непонятно, кто виноват), и не должно быть строк без R.

Шаг 4: Согласовать матрицу со всеми, зафиксировать письменно и обращаться к ней при каждом конфликте.

**Разбор двух задач из матрицы:**

Общение с заказчиком: аналитик несёт полную ответственность (A) — он единственная точка контакта. Остальные только получают информацию (I). Это убирает ситуацию, когда заказчику звонят все по очереди с разными сообщениями.

Проверка качества кода: второй разработчик — ответственный (A), первый разработчик делает код-ревью (R), тестировщик консультирует по критериям качества (C). Это означает: разработчики проверяют друг друга, тестировщик помогает с критериями, но конечное решение «принять/отклонить» за разработчиком 2.

## Кейс 5. «Методология для кризиса»

**Строительство моста (Waterfall):**

Waterfall — последовательная методология: требования → проектирование → строительство → сдача. Для моста это единственный разумный выбор по трём причинам. Первое: требования фиксированы изначально — мост должен выдерживать конкретную нагрузку, иметь конкретные размеры, стоять в конкретном месте. Второе: государственный заказчик требует отчётности на каждом этапе — фазовый подход Waterfall идеально это обеспечивает. Третье: цена и сроки фиксированы, переделывать фундамент после укладки асфальта невозможно ни технически, ни финансово.

**Разработка приложения для доставки еды (Agile + Lean):**

Здесь требования меняются каждую неделю — это сигнал для Agile. Конкретно: Scrum с 1–2-недельными спринтами, после каждого — живая демонстрация заказчику. Lean добавляет принцип «не делай то, что не нужно прямо сейчас»: никакой избыточной документации, никакой архитектуры «на будущее». Делаем только то, что проверено пользователями.

Комбинация Waterfall + Agile (так называемый Wagile) применяется в крупных IT-проектах с госзаказчиком: верхний уровень планирования — водопад (фазы, контрольные точки), внутри каждой фазы — Agile-итерации.

## Кейс 6. «CJM для фитнес-клуба»**Четыре ключевые боли, не связанные с ценой:**

Первая — отсутствие «тёплого» приёма. Человек приходит в первый раз, никто его не встречает, не показывает клуб, не объясняет правила. Он чувствует себя чужим и лишним. Решение: выделить «buddy» — администратора или тренера, который первые 10 минут посвящает новичку.

Вторая — слишком высокая нагрузка на первой тренировке. Тренер хочет показать результат, даёт сложную программу. Клиент уходит домой с дикой болью в мышцах и больше не возвращается, потому что ассоциирует клуб с болью, а не с удовольствием.

Третья — отсутствие follow-up после пробной тренировки. Клуб не звонит, не пишет, не спрашивает «как вам было?». Клиент ждёт сигнала, что его ждут — и не получает его.

Четвёртая — неудобный процесс онлайн-присутствия. Нет записи через сайт, нет чёткой информации о расписании и тренерах, мало реальных фото. Первый контакт происходит ещё до прихода в клуб — и он уже вызывает трение.

## Кейс 7. «5 почему» — текучка в ИТ-компании

Метод «5 почему» — последовательное углубление: каждый ответ становится новым вопросом.**Итоговая гипотеза:** корневая проблема не в зарплате, а в отсутствии технического развития и карьерных перспектив. Разработчики уходят к работодателям, которые дают возможность работать с новыми технологиями, расти профессионально и влиять на архитектуру продукта.

**Что делать:** ввести «технические дни» (20% времени на R&D), составить индивидуальные планы развития (IDP), начать постепенный рефакторинг с реальными задачами, дать senior-разработчикам роль технических менторов.

## Кейс 8. «Unit-экономика подписки»

**Расчёт unit-прибыли на одну подписку:**

Выручка с одной подписки: 500 руб.

Переменные расходы на одну подписку:

- CAC (стоимость привлечения): 200 руб.
- COGS: 250 руб./порция × 4 порции = 1000 руб.

Итого переменные расходы: 200 + 1000 = **1200 руб.**

Unit-прибыль = 500 − 1200 = **−700 руб.** на подписку.

Это критическая ситуация: каждая продажа приносит убыток 700 рублей. Бизнес убыточен на уровне unit-экономики, даже не доходя до постоянных расходов.

**Точка безубыточности:**

Поскольку каждая единица убыточна, математически невозможно выйти в ноль при данной модели, увеличивая количество подписок. Чем больше продаёшь — тем больше теряешь.

Чтобы задача имела решение, нужно пересчитать: если допустить, что CAC — единовременная инвестиция (а не на каждого клиента каждый месяц), то маржа на подписку = 500 − 1000 = −500 руб. Всё равно отрицательная.

**Что делать при 300 подписках и цели 500:**

Проблема структурная, не в объёме. Нужно одно или несколько из следующего:

Поднять цену: если средняя стоимость порции здоровой еды — 250 руб., то цена подписки 500 руб. за 4 порции — это продажа себе в убыток. Реальная цена должна быть минимум 1500–2000 руб., чтобы покрыть COGS.

Снизить COGS: оптовые закупки, собственная доставка вместо курьерских сервисов, сокращение упаковочных расходов.

Снизить CAC: органический трафик (контент, сарафан), реферальная программа (клиент приводит клиента за скидку).

Повысить LTV: удержать клиента на несколько месяцев — тогда CAC «размазывается» и становится терпимым.

## Кейс 9. «Геймификация для уборки»

Штрафы — это внешняя негативная мотивация, которая создаёт сопротивление и ухудшает атмосферу. Геймификация использует внутреннюю мотивацию через игровые механики.

**Идея 1 — «Стол месяца» (социальный статус + соревнование):** на каждом столе — QR-код. Посетитель, убравший за собой, сканирует его и получает «очки чистоты» на свой профиль в приложении или карте. Топ-10 самых аккуратных посетителей отображаются на экране у входа. Победитель месяца получает бесплатный месяц коворкинга. Метрика: % столов, убранных после использования (кассир или камера фиксирует).

**Идея 2 — «Чистая зона» (коллективная награда):** каждый зал получает свой «уровень чистоты» — от 1 до 5. Если зал за неделю не получил ни одной жалобы на беспорядок, все резиденты этого зала получают бонус: дополнительный час бесплатного доступа или скидку на кофе. Это создаёт социальное давление внутри сообщества — люди напоминают друг другу убирать, потому что это выгодно всем. Метрика: количество нарушений в неделю по залу.

**Идея 3 — «Экологический прогресс» (нарратив и ценности):** на стенах — счётчик «Вместе мы сэкономили X кг уборочных химикатов, потому что убираете сами». Людям важно чувствовать, что они делают мир лучше. Маленький визуальный прогресс-бар превращает уборку из обязанности в вклад. Метрика: общее количество самостоятельно убранных столов в месяц.

## Кейс 10. «Кто заказывал исследование?»

**Где ошибка в постановке задачи:**

Менеджер совершил классическую ошибку — перешёл к решению (онлайн-опросы среди всех возрастов), не поняв задачу заказчика. Заказчику нужен был инструмент для запуска продукта, а не абстрактное «исследование поведения». Это разные цели: одна — академическая, другая — операционная.

**Вопросы, которые нужно было задать на старте (фрейминг задачи):**

— «Какое решение вы примете на основе этого исследования?» — это ключевой вопрос. Если заказчик не может ответить, значит, он сам не понимает, зачем ему исследование.

— «Кто ваш целевой покупатель — возраст, образ жизни, где покупает соки сейчас?» — это сужает выборку.

— «Что уже известно о рынке? Что конкретно непонятно?» — чтобы не исследовать то, что уже исследовано.

— «Какой срок запуска продукта и какие решения нужно принять до него?» — исследование должно быть привязано к бизнес-таймлайну.

**Как фрейминг мог помочь:**

Фрейминг — это переосмысление задачи до начала работы. Правильный фрейм: «нам нужно понять, почему наша целевая аудитория (например, женщины 25–35 лет, ЗОЖ) выберет именно наш сок на полке». Тогда метод исследования — не онлайн-опрос по всем возрастам, а качественные интервью с 15–20 представителями ЦА + анализ полки в магазине. Результат был бы применим для запуска.

## Кейс 11. «Рынок идей для пенсионеров»

**Почему это плохой CustDev:**

Молодые люди — не потребители сервиса. Они не будут им пользоваться, не знают реальных барьеров (оплата наличными — это не просто «способ оплаты», это вопрос доверия и привычки), не понимают страхов и потребностей пожилых людей. Их одобрение («крутая идея») — это социальная вежливость, а не валидация гипотезы. Это называется «confirmation bias» — искать подтверждение там, где его легко найти.

**Кого нужно интервьюировать:**

В первую очередь — одиноких пенсионеров 70+ лет, которые живут самостоятельно и имеют ограниченную мобильность. Во вторую очередь — их детей и родственников, которые часто являются «агентами принятия решений» (именно они договариваются об услугах для родителей). В третью — социальных работников, которые уже работают с этой аудиторией и знают реальные боли.

**Правильные вопросы для интервью:**

— «Расскажите, как вы сейчас решаете вопрос с покупкой продуктов? Кто вам помогает?» — открытый вопрос, выявляет текущее поведение.

— «Были ли случаи, когда вам было сложно получить продукты? Что произошло?» — выявляет реальные болевые точки, а не гипотетические.

— «Если бы к вам домой мог приходить курьер с продуктами, что было бы для вас самым важным?» — приоритеты: надёжность, знакомое лицо, конкретные продукты, цена.

## Кейс 12. «Постоянные vs переменные»

**Разделение расходов:**

Постоянные (не зависят от количества студентов): аренда веб-сайта — 10 000 руб./мес.

Переменные (растут с каждым студентом/уроком):

- Зарплата преподавателя: 500 руб./урок. Если в курсе, допустим, 10 уроков, то на одного студента — 5000 руб.
- Реклама: 300 руб. за одного пришедшего студента (это фактически CAC).

**Расчёт точки безубыточности:**

Цена курса: 2000 руб. Переменные затраты на студента: 5000 (преподаватель) + 300 (реклама) = 5300 руб.

Маржа на студента = 2000 − 5300 = **−3300 руб.**

Здесь та же ситуация, что в кейсе 8: unit-экономика отрицательная. Допустим, задача предполагает, что урок — это групповой, и стоимость преподавателя делится между студентами. Если в группе 10 человек:

Затраты преподавателя на студента = 500 × 10 уроков / 10 студентов = 500 руб.

Переменные затраты на студента: 500 + 300 = 800 руб. Маржа на студента = 2000 − 800 = **1200 руб.**

Формула точки безубыточности: Постоянные затраты / Маржа на студента = 10 000 / 1200 = **9 студентов** — минимум для нулевой прибыли.

**Для прибыли 50 000 руб.:** (10 000 + 50 000) / 1200 = 60 000 / 1200 = **50 студентов**.

## Кейс 13. «Конфликт в команде проекта»

**План действий на 1 неделю:**

День 1 — Фрейминг проблемы. Не «у нас ленивые участники», а «у нас не распределена ответственность, и люди не понимают, что именно от них ждут». Провести встречу, на которой озвучить ситуацию без обвинений: «Мы в риске срыва дедлайна. Давайте вместе разберёмся, кто что делает».

День 2 — RACI-матрица. Составить список всех оставшихся задач проекта. Совместно распределить роли. Каждый должен иметь хотя бы одну задачу с ролью R (исполнитель). Зафиксировать письменно.

День 3–4 — Мини-спринт в стиле Agile. Каждый участник называет, что он сделает за следующие 2 дня (конкретный результат, не процесс). Это создаёт публичное обязательство — психологически намного сильнее, чем общая договорённость.

День 5 — Ретроспектива. Провести короткую встречу: «Что сделали? Что мешало?». Это честный срез без обвинений. Если кто-то снова не выполнил — разговор тет-а-тет с руководителем группы: «Что произошло? Как я могу помочь?»

Инструмент дизайн-мышления здесь — эмпатия к «ленивым» участникам. Возможно, они не понимают задач, боятся ошибиться, или перегружены другими обязательствами. HADI-цикл можно применить к самому конфликту: гипотеза — «людям не хватает ясности задач», действие — RACI, измерение — выполнение задач за неделю.

## Кейс 14. «Подрядчик сорвал сроки»

**Что делать прямо сейчас:**

Шаг 1: Зафиксировать факты письменно — что было обещано, что получили, в каком состоянии. Это доказательная база.

Шаг 2: Провести переговоры с подрядчиком. Не с позиции «вы нас обманули», а с позиции «у нас проблема, давайте её решим». Возможные варианты: доделать за сниженную цену, вернуть часть аванса, дать чёткий дедлайн с последствиями.

Шаг 3: Нанять другого подрядчика доделать работу, если первый не реагирует — и заложить эти расходы в претензию к первому.

Шаг 4: Минимизировать потери клиентов — поставить временную страницу-заглушку с объяснением и контактами.

**Что нужно было сделать при выборе подрядчика:**

Запросить портфолио и поговорить с реальными клиентами подрядчика (не с теми, кого он сам называет). Попросить смету с разбивкой по этапам. Проверить юридическое лицо — не работать с физлицами без договора. Выбирать из нескольких кандидатов, а не с первым, кто откликнулся.

**Ключевые элементы договора с подрядчиком:**

Первый — поэтапная оплата, привязанная к конкретным результатам (не «30% аванс», а «30% — после утверждения макетов, 40% — после тестовой версии, 30% — после сдачи»).

Второй — чёткие критерии приёмки: что значит «готов лендинг». Количество страниц, скорость загрузки, совместимость с браузерами.

Третий — штрафные санкции за просрочку (например, 1% от суммы за каждый день задержки).

Четвёртый — передача прав на код и исходники при финальной оплате, и возврат исходников при расторжении договора.

## Кейс 15. «Инновация в госсекторе»

**Модель взаимодействия без прямого финансирования:**

Ключевая идея: государство платит не деньгами, а другими ресурсами — доступом, данными, легитимностью и рекламой.

**Тип партнёрства 1 — Пилотный проект с правом публичного кейса.** Министерство предоставляет компании доступ к студенческим работам (обезличенным) для обучения модели и тестирования. Компания получает право публично называться «партнёром Министерства образования» — это колоссальная PR-ценность для B2B-продаж в другие вузы и регионы. Министерство получает работающий инструмент бесплатно или по льготной цене.

**Тип партнёрства 2 — Государственно-частное партнёрство (ГЧП) с монетизацией через другие каналы.** Компания разрабатывает AI-помощника, встраивает в него рекламный модуль (например, партнёры — образовательные платформы, издательства). Министерство не получает рекламных прав на саму систему, но получает чистый интерфейс для студентов. Компания монетизирует через рекламу внутри системы.

**Тип партнёрства 3 — Freemium для госсектора.** Компания предоставляет базовую версию AI-проверки бесплатно для государственных вузов. Платные функции (детальная аналитика, интеграция с LMS, отчёты для деканата) продаются платно. Министерство получает бесплатный инструмент, компания — тысячи пользователей для обучения модели и воронку продаж платного тарифа.

**Нефинансовые форматы взаимодействия:** ускоренное согласование нормативных документов, рекомендательные письма для других регионов, включение в официальный реестр EdTech-партнёров, доступ к анонимизированным данным для R&D.
